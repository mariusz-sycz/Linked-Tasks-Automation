Speed Up Task Creation, Progress Feedback & Popup-Close Reliability

TL;DR

The click-to-first-task delay is a single, strictly sequential Q-promise chain with zero UI feedback and two needlessly nested (but independent) REST calls; real but partial parallelization headroom exists in the per-template create loop. All three sub-questions (preload/async, progress UI, popup-close survival) converge on the same root constraint: the extension's only contribution (ms.vss-web.action → invisible, dialog-scoped toolbar.html) has no pre-click load moment, no visible rendering surface, and is very likely torn down when its hosting work-item dialog closes. Cheap, no-manifest-change wins exist for (a) and a partial fix for (b); a robust fix for (b) and (c), and true pre-click preload for (a), all require adding a persistent/visible contribution surface not scoped to the work-item dialog.

Key Decisions

  • Split remediation into a point-fix track (no manifest change) and an architecture track (new contribution surface) — three gatherers converged on the same structural cause from unrelated angles.
  • Recommend localStorage over IExtensionDataService (no latency advantage, adds a REST round trip) or IndexedDB (unnecessary complexity, unshimmed, risk of silent failure) for template caching.
  • Do NOT blanket-parallelize the per-template create loop — only templates without justCreatedTasks-referencing linkTo rules can safely run concurrently.

Open Questions / Risks

  • Popup-close root cause rests on a documented category contrast (observer vs. form-scoped contributions), not a verbatim statement about this exact contribution type, and is not live-verified (no ADO org available).
  • Whether the toolbar iframe is ever reused (vs. always freshly created) across clicks is unresolved — affects only an optional in-memory cache layer.
  • Runtime resolution of the q AMD promise library in the packaged .vsix is unconfirmed.

Key Insights

1"Preload after plugin load" is not literally reachable

Static manifest-declared menu text means the host never loads toolbar.html before the click. True pre-click preload needs a new, earlier-loading contribution.

Medium confidence

2The "popup" bug is really a "dialog-scoped contribution" bug

Any fix that keeps the trigger inside the work-item toolbar/context menu inherits the same fragility, regardless of how app.ts's async flow is restructured.

Medium-High confidence

3Blanket parallelization would break existing templates

PreviouslyCreatedTask/FirstJustCreatedTask/etc. depend on alphabetical creation order having already resolved. Only templates without these rules can safely run concurrently.

High confidence

4localStorage dominates for this caching use case

IExtensionDataService adds a REST round trip with no latency win; IndexedDB adds complexity with no capacity benefit and no SDK shim safety net.

High confidence

5A modal "done" dialog is the cheapest available win — but isn't what was asked for

IHostDialogService.openMessageDialog is the only API confirmed to render in the visible host frame from this contribution type, but it is modal — good for a final "5 of 5 created" summary, not live in-flight, non-blocking progress.

High confidence

Remediation Tracks

Point-fix track — ship now, no manifest change
  • Cache templates in localStorage, check-cache-first in create()/AddTasks()
  • Parallelize getTeamSettings/getWorkItem via Promise.all/Q.all
  • Selectively parallelize template creates without justCreatedTasks-dependent linkTo rules
  • Modal end-of-run summary via IHostDialogService.openMessageDialog
Architecture track — resolves (b) and (c) robustly, upgrades (a)

Add a persistent/visible contribution surface (hub or work-item-form-page) not scoped to the work-item dialog. Single investment, three benefits — recommended as one decision for the solution-design phase, not three separate point solutions.

Quality Assessment — Current Implementation

Strengths

  • Existing fan-outs (getTemplates, GetChildTypes) already use Q.all correctly
  • Link creation already decoupled (fire-and-forget) from the main chain
  • ES2015 compile target — native Promise/async/await available if desired

Weaknesses

  • Zero UI feedback anywhere in the flow
  • Two independent REST calls needlessly nested
  • Per-template loop over-serialized
  • No user-facing error surfacing (console-only)

Opportunities

  • No-manifest-change wins available today
  • One architecture investment resolves (b) and (c) together

Threats / Risks

  • Blanket parallelization could silently break positional linking rules
  • Popup-close root cause not live-verified
  • q module runtime resolution unconfirmed

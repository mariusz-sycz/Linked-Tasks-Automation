TL;DR

Three interdependent decision areas: (1) which contribution surface hosts execution/UI, (2) caching strategy, (3) progress-feedback mechanism — (2) and (3) are constrained by (1)'s outcome. Recommended path: ship point-fixes now (localStorage caching, safe parallelization, live-updating modal progress dialog — no manifest change, resolves (a) partially and (b) partially); adopt a Hybrid contribution architecture (keep today's toolbar/context-menu trigger, add a Hub contribution as a decoupled execution+progress engine) as the target state that fully resolves (b) and (c); fall back to a pure Hub (trigger moves too) if the hand-off design proves too risky.

Key Decisions

  • Decision Area 1 (contribution surface) is the shared prerequisite — present it to the user first; Decision Areas 2 and 3 branch on its answer.
  • Caching strategy: "lazy now, eager-when-available later" — forward-compatible with whichever Decision Area 1 outcome is chosen.
  • Progress feedback: skip the plain end-of-run modal in favor of a live-updating modal dialog as the near-term fix — same API, more informative for negligible extra effort.
  • Do not pursue a toast/GlobalProgressIndicator "middle option" — no evidence either control crosses into the host frame from this contribution type.

Open Questions / Risks

  • Whether dialog close actually tears down the current action contribution's iframe (the root-cause claim driving this exploration) is Medium-High confidence, not live-verified.
  • Whether a work-item-form-page contribution survives dialog close is explicitly unverified — the swing factor for Alternative 2's viability.
  • The Hybrid architecture's action-click → hub hand-off has no precedent in the research — needs a feasibility spike before being treated as committed.
  • Whether adding a Hub contribution alongside an existing action contribution has any Marketplace/manifest constraint was not investigated.

Problem Reframing

Research Question: How can the extension (a) preload/cache templates and create tasks/links asynchronously so the user isn't blocked after clicking "create"; (b) show a visible, non-blocking progress indicator while creation is in flight; and (c) keep creating tasks in the background even if the popup is closed, stopping only on a full page refresh?

How Might We:

  • HMW make creation resilient to the user closing the dialog immediately after clicking? Decision Area 1
  • HMW give users a live, truthful sense of progress without freezing their view of Azure DevOps? Decision Area 3, constrained by Area 1
  • HMW get templates ready before the user ever clicks — not just faster on click #2? Decision Area 1 & 2
  • HMW cache templates so repeat invocations feel instant, in a way that upgrades cleanly if architecture changes? Decision Area 2
1

Decision Area 1: Contribution Surface

Why this comes first: the shared prerequisite for a robust fix to (b) and (c), and it materially upgrades (a) from "faster on click #2" to true pre-click preload.

Alt 1

Minimal Change — Point-Fixes Only

Keep the single existing action contribution. Apply only no-manifest-change fixes: caching, safe parallelization, modal dialog.

  • + Zero UX disruption, fastest, lowest risk
  • − Doesn't resolve (b)/(c) genuinely
Alt 2

Work-Item-Form-Page Contribution

New tab/section in the work item form, visible while the form is open.

  • + Visible DOM, stays in work-item context
  • − Dialog-close survival unverified; still form-scoped
Alt 3

Hub Contribution

New persistent nav page, fully decoupled from any work item dialog.

  • + Cleanest evidenced fix for (b)/(c)
  • − Biggest UX/discoverability change — moves the trigger
Alt 4

Observer Contribution (paired)

Headless observer, documented to survive dialog close, paired with a UI surface.

  • + Strongest single evidence for (c)
  • − Headless; click-to-observer hand-off unverified
Recommended target
Alt 5

Hybrid — Action Trigger + Hub-Hosted Engine

Keep today's trigger; hand off execution to a decoupled Hub via a localStorage job record.

  • + No trigger UX change, full (b)/(c) resolution
  • − Highest complexity; novel hand-off, load-race risk
2

Decision Area 2: Caching Strategy

Depends on Decision Area 1: a persistent surface can warm the cache eagerly on load; a dialog-scoped surface only ever gets a click-time check. Storage mechanism (localStorage) is settled — these alternatives differ only in strategy.
Alt 1

Reactive Lazy Caching

Check cache, else fetch, on every invocation.

  • + Simplest, works under any Area 1 outcome
  • − Click #1 always pays full latency
Alt 2

TTL + Stale-While-Revalidate

Lazy read with TTL; background refresh on hit.

  • + Guards against stale templates
  • − Added complexity, likely premature here
Alt 3

Eager Cache Warming

Warm cache on new surface's load, before any click.

  • + True pre-click preload, satisfies (a) literally
  • − Needs Area 1's persistent surface first
Recommended
Alt 4

Hybrid — Lazy Now, Eager When Available

Ship Alt 1 today; same code path upgrades to Alt 3 once a surface exists.

  • + Forward-compatible, no rework later
  • − Slightly more upfront design discipline
3

Decision Area 3: Progress Feedback

Depends on Decision Area 1: only IHostDialogService.openMessageDialog is confirmed to reach the host frame from the current surface — and it's modal. Genuinely live, non-blocking progress requires Area 1's new visible surface.
Alt 1

Modal End-of-Run Summary

One dialog after everything finishes.

  • + Available today, cheapest
  • − Not in-flight, not non-blocking; dominated by Alt 2
Recommended near-term
Alt 2

Live-Updating Modal Progress Dialog

Same API, opened on click, updated as each template resolves.

  • + Real in-flight visibility, no manifest change
  • − Still modal (blocks interaction)
Alt 3

Toast / Notification "Middle Option"

Investigated per brief — periodic host-frame toasts.

  • + Would be non-blocking if it worked
  • − No evidence it's reachable from this contribution type. Not recommended.
Alt 4

True Live Progress in New Surface

Real progress bar in Area 1's new visible surface once it lands.

  • + Fully satisfies "visible, non-blocking, in-flight"
  • − Gated on Area 1's architecture landing

Recommended Approach

Decision Area 1: Ship Alternative 1 (minimal change) immediately. In parallel, adopt Alternative 5 (Hybrid) as the target architecture — the only option resolving (b)/(c) without changing the trigger UX. Fall back to Alternative 3 (pure Hub) if the hand-off proves unreliable. Alternative 2 (form-page) is contingent on live verification; Alternative 4 (observer) is a possible later addition, not a starting point.

Decision Area 2: Adopt Alternative 4 (lazy now, eager when available) — a strict improvement over plain lazy caching at negligible extra cost.

Decision Area 3: Adopt Alternative 2 (live-updating modal) near-term; replace with Alternative 4 (true live progress) once the architecture track lands. Skip Alternative 3 (toast) — unevidenced.

Confidence: Medium. High confidence in point-fix mechanisms; medium confidence in the architecture recommendation, since it depends on claims the research itself flags as not live-verified (Report Recommendation 6).

Why Not Others

Decision Area 1

  • Alt 2 (form-page) — the claim needed to make it competitive (survives dialog close) is unverified and viewed with skepticism per the evidence.
  • Alt 3 (pure Hub) — fully resolves (b)/(c) but at the UX cost the brief specifically asked to weigh; Hybrid achieves the same outcome without it, at higher build cost.
  • Alt 4 (observer alone) — headless, cannot resolve (b) without a paired surface, making it redundant as a standalone starting point.

Decision Area 2

  • Alt 1 (plain lazy) — Alt 4 delivers identical near-term behavior with no future rewrite; no scenario favors it over Alt 4.
  • Alt 2 (TTL/SWR) — adds complexity for a staleness problem not evidenced as real in a stable/maintenance extension.
  • Alt 3 (eager only) — can't ship until Area 1 resolves; already included as a phase within Alt 4.

Decision Area 3

  • Alt 1 (end-of-run modal) — strictly dominated by Alt 2, same API, more useful information.
  • Alt 3 (toast) — no evidence it's reachable from the host frame in this contribution type; would require redoing platform research already completed.
Deferred Ideas
  • Migrating the promise chain off Q to native Promise/async/await — orthogonal to all three decision areas.
  • IExtensionDataService-based cross-device/cross-browser template durability — deprioritized, no latency advantage, not a stated requirement.
  • Fixing the pre-existing bugsBehavior numeric-enum-vs-string-literal bug in GetChildTypes — real defect, but unrelated to this research's scope.
  • Full server-side/backend component for truly detached execution — sidesteps the core constraint but explicitly out of scope (stateless, browser-only extension).

TL;DR

Keep the extension's single existing ms.vss-web.action contribution — no Hub, no observer, no form-page tab, overriding solution-exploration.md's top Hybrid-architecture recommendation per explicit user convergence. Fix popup-close fragility by switching create/link REST calls from the wrapped SDK client to raw fetch(url, { keepalive: true }), which survives iframe teardown but cannot chain on a response after the popup closes — so templates whose linkTo rules depend on justCreatedTasks (and any template's own link-to-parent step) remain exposed if the popup closes mid-chain. Templates and parallelizable REST reads get localStorage-backed caching with a 4-hour TTL (no event-driven invalidation exists — verified infeasible). Progress feedback uses two IHostDialogService.openMessageDialog calls (start/end); design-time inspection of the SDK typings found this API has no programmatic close handle, so the "auto-dismiss after 5s" ask from convergence is not achievable as literally stated.

Key Decisions

  • No new contribution surface; Hub/Hybrid explicitly rejected for this iteration — ADR-001.
  • Creates/links move to fetch(keepalive:true) with a bearer token from VSS.getAccessToken(); ordering-dependent templates and every template's link-to-parent step remain vulnerable to popup close before dispatch — accepted limitation — ADR-002.
  • Template caching: localStorage, lazy population, 4-hour TTL (configurable); event-driven invalidation confirmed infeasible — ADR-003.
  • Progress feedback: two openMessageDialog calls, single pre-focused button each; true timer-driven auto-close not implementable against the confirmed API — ADR-004.
  • getTeamSettings/getWorkItem parallelized; template creates split into concurrent "independent" and sequential "ordered" groups — ADR-005.

Open Questions / Risks

  • openMessageDialog has no SDK-confirmed way to close programmatically — re-confirm "two single-click dialogs, no auto-timer" with the product owner before implementation.
  • Popup-close survival is not guaranteed for ordering-dependent creates or any not-yet-dispatched link call — communicate as the actual behavior, not full survival.
  • Exact REST endpoint/api-version for fetch-based calls should be confirmed against the wrapped client's actual network traffic at implementation time, not guessed.
  • 4h TTL and cache-key scheme are sensible defaults, not hard requirements — tune during implementation.
  • Shimmed vs. native localStorage path in the real deployment target is unconfirmed — minor write-timing nuance only.

Design Overview

Business context: Linked Tasks Automation is a stable, in-production Azure DevOps extension that creates templated child work items from a parent with one click. Users get zero feedback during creation, and closing the work-item dialog immediately after clicking silently kills any in-flight task creation.

Chosen approach: Keep the extension's single existing contribution unchanged — no Hub, no observer, no form-page tab — reversing solution-exploration.md's top-recommended Hybrid architecture per explicit convergence favoring simplicity. Popup-close survival is addressed via raw fetch with keepalive: true for creates/links. Templates are cached in localStorage with a TTL. Progress is surfaced via two IHostDialogService.openMessageDialog calls — necessarily modal, and without a programmatic close handle (a design-time finding).

Concrete Examples

1. Independent templates survive popup close. Three Task templates with no ordering linkTo rule; user closes the popup ~150ms after clicking create. All three creates were already dispatched via fetch(keepalive:true), so all three work items are created regardless. Each template's link-to-parent call succeeds only if its create's response was read before the popup closed.

2. Ordering-dependent template exposed to popup close. "Task A" (no linkTo) and "Task B" (linkTo: PreviouslyCreatedTask); popup closes 50ms after click, before Task A's response is read. Task A's create still completes via keepalive; Task B's create never fires because the ordered chain died with the iframe before reaching it — the accepted, documented limitation.

3. Cache TTL staleness trade-off. User creates linked tasks twice, 20 minutes apart. Second click serves templates from localStorage, skipping REST round trips. If a template was edited via Team Settings in between, the second click still uses the stale version until the 4-hour TTL expires — accepted, since no invalidation event exists.

Out of Scope

  • Any Hub, observer, or work-item-form-page contribution (ADR-001)
  • Guaranteed popup-close survival for ordering-dependent creates/links (ADR-002)
  • True non-blocking (non-modal) in-flight progress UI
  • Programmatic auto-dismiss of progress dialogs after a fixed delay (ADR-004)
  • Event-driven cache invalidation (ADR-003)
  • Full Q-library migration across the rest of the codebase
  • IExtensionDataService-based cross-device cache durability
  • Fixing the pre-existing bugsBehavior bug in GetChildTypes
  • Automated tests for this feature (no test framework exists yet)

Success Criteria

  1. Repeat invocations within the TTL skip getTemplates/getTemplate entirely.
  2. getTeamSettings and getWorkItem execute concurrently, not nested.
  3. Non-ordering-dependent templates create concurrently, with no linking-behavior change vs. today.
  4. Any create dispatched before popup close results in a created work item, even if the popup closes immediately after.
  5. User sees an immediate start acknowledgment and, if the popup stays open, a completion summary.
  6. Ordered-group templates produce identical output to current behavior.

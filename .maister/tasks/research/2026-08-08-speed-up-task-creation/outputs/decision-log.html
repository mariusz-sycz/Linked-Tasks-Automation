Decision Log: Speed Up Task Creation, Progress Feedback, Popup-Close Reliability

5ADRs total
5accepted
0rejected / superseded

TL;DR

Five ADRs, all reflecting the simpler path chosen during interactive convergence over solution-exploration.md's top-recommended Hybrid architecture. The most consequential: ADR-001 rejects any new contribution surface, which forces ADR-002's fetch(keepalive:true) create/link approach and ADR-004's still-modal dialog feedback to accept real, documented limitations rather than fully solving popup-close survival and non-blocking progress. ADR-003 settles caching (localStorage + TTL) after live-verifying that event-driven invalidation is not possible on this platform. ADR-004 additionally surfaces a design-time finding — openMessageDialog has no programmatic close handle — that narrows what "self-dismissing" can mean in implementation.

Key Decisions

  • ADR-001: No new contribution surface — Hub/Hybrid rejected for this iteration.
  • ADR-002: fetch(keepalive:true) replaces the wrapped REST client for creates/links only, with an accepted response-chaining limitation.
  • ADR-003: localStorage + TTL caching; event-driven invalidation ruled out as infeasible.
  • ADR-004: Two openMessageDialog calls for progress feedback; programmatic auto-close not achievable.
  • ADR-005: Parallelize independent reads and non-ordering-dependent template creates.

Open Questions / Risks

  • ADR-004's "self-dismissing" framing should be re-confirmed with the product owner as "two single-click dialogs, no auto-timer" before implementation.
  • ADR-002's popup-close protection does not extend to ordering-dependent creates or not-yet-dispatched link calls — communicate as actual behavior, not full survival.
  • ADR-005's classification logic must stay in sync if new linkTo rule types are added later.

Contents: ADR-001 · ADR-002 · ADR-003 · ADR-004 · ADR-005

Accepted

ADR-001: No New Contribution Surface — Reject Hub/Hybrid Architecture

Context

solution-exploration.md recommended shipping point-fixes immediately while adopting a Hybrid (action trigger + Hub-hosted execution engine) as the target architecture. During convergence, the user explicitly chose to stay within the existing single ms.vss-web.action contribution instead.

Decision Drivers

  • Hybrid/Hub is the highest-complexity alternative of five evaluated — two contributions, a novel hand-off protocol with no SDK precedent, an unresolved race condition.
  • Extension is in stable/maintenance mode with an established user base; a Hub changes discoverability/navigation.
  • fetch(keepalive:true), verified live during convergence, reduces the marginal benefit of the Hub for popup-close resilience.
  • Marketplace/manifest constraints on adding a Hub were never investigated — unresolved risk a simpler design avoids.

Considered Options

  1. Hybrid (action + Hub)
  2. Pure Hub
  3. Work-item-form-page contribution
  4. Observer contribution, paired
  5. No new contribution surface — SELECTED

Decision Outcome

Option 5: preserves today's UX/trigger, zero manifest change, lowest risk, and combined with ADR-002 closes enough of the gap without the Hybrid's unresolved hand-off risk.

Consequences

Good: zero manifest/UX disruption; lowest risk/effort; ships fastest.

Bad: no fully non-blocking progress (ADR-004); no guaranteed popup-close survival for every case (ADR-002); Hub/Hybrid remains a deferred future escalation, not avoided permanently.

Accepted

ADR-002: fetch(keepalive:true) Replaces the Wrapped REST Client for Creates and Links

Context

app.ts calls witClient.createWorkItem (:110) and witClient.updateWorkItem (via linkItems, :217) inside the toolbar.html iframe. Iframe teardown on popup close aborts in-flight requests (research Finding 9). fetch's keepalive option, verified live during convergence, lets a request continue past the frame that started it — but not any code reading its response.

Decision Drivers

  • Must operate within ADR-001's no-new-surface constraint.
  • keepalive is a browser-platform guarantee, lowering platform risk vs. unverified SDK lifecycle claims.
  • Does not keep the JS execution context alive — any step reading a prior response is unprotected.

Considered Options

  1. Status quo (wrapped client, full fragility)
  2. New persistent surface (superseded by ADR-001)
  3. Raw fetch(keepalive:true) for creates/links only, reads stay on wrapped client — SELECTED

Decision Outcome

Option 3: targets the exact failure mechanism, no manifest change, confines new calling pattern to exactly where "survive popup close" matters.

Consequences

Good: dispatched create/link requests complete server-side even after popup close; no manifest change; reads unaffected.

Bad: ordering-dependent (justCreatedTasks) templates whose create hasn't been dispatched at close time never fire; every template's link-to-parent call (:120) and the ToAllOtherChilds link path (:85-102) remain exposed if the popup closes between a read/create and its dependent link call; two REST-calling patterns now coexist; auth is now handled per-call via VSS.getAccessToken().

Accepted

ADR-003: localStorage + TTL Template Caching; Event-Driven Invalidation Rejected as Infeasible

Context

Templates are re-fetched on every invocation today (Finding 1) despite changing infrequently. localStorage survives iframe teardown (Finding 6). Convergence asked specifically whether event-driven invalidation (reacting to template save) was feasible.

Decision Drivers

  • Cache must survive iframe teardown between invocations — only localStorage qualifies.
  • Template edits should surface automatically within a bounded window, no manual cache-clear.
  • Verified live against Microsoft's Extensibility Points reference: no extensibility point exists for template create/save — hubs, menus, toolbars, tabs, dashboard widgets, work-item-form, Service Hooks all checked, none apply. Infeasible, not just deprioritized.

Considered Options

  1. Plain lazy caching, no TTL
  2. TTL + stale-while-revalidate
  3. Eager warming on load (needs a persistent surface — foreclosed by ADR-001)
  4. Event-driven invalidation — confirmed infeasible
  5. Lazy population + TTL, no background revalidation — SELECTED

Decision Outcome

Option 5: zero manifest change, no event source needed, bounds staleness without stale-while-revalidate's added bookkeeping for an infrequently-changing data profile.

Consequences

Good: repeat invocations within TTL skip the fetch entirely; edits picked up automatically within a bounded window; simplest correct option.

Bad: edits can take up to the full TTL (default 4h) to appear; default is a starting point, not empirically tuned.

Accepted

ADR-004: Self-Dismissing Modal Dialog for Progress Feedback — With a Confirmed API Limitation

Context

IHostDialogService.openMessageDialog is the only API confirmed to reach the host frame (Finding 7), and is modal. Convergence asked for a two-call pattern that auto-dismisses after ~5s. Design-time inspection of vss.d.ts:646-654 vs. 535-562 found openMessageDialog returns only IPromise<IMessageDialogResult> — no IExternalDialog handle. Only openDialog returns a closeable IExternalDialog, and it requires a contributed control — itself a new contribution, contradicting ADR-001.

Decision Drivers

  • Must stay within ADR-001 — rules out openDialog's contributed-control path.
  • Must give an immediate acknowledgment plus a later completion summary.
  • A setTimeout-driven .close() has no handle to call — not implementable as literally requested.

Considered Options

  1. Single end-of-run modal only
  2. "Live-updating" single modal — not implementable, no update method exists
  3. Toast / GlobalProgressIndicator — already rejected (no host-frame reach)
  4. Two openMessageDialog calls (start + completion), single default button each, no programmatic auto-close — SELECTED

Decision Outcome

Option 4: closest approximation to convergence's intent within the API's real capabilities; the literal timer-based auto-dismiss is flagged as not implementable, not silently built.

Consequences

Good: no new contribution; immediate acknowledgment plus completion summary when reachable; one click/Enter dismisses each dialog.

Bad: still genuinely modal while open; no programmatic auto-close is possible — needs a scope conversation with the product owner before implementation; completion dialog only appears if the popup is still open when tracked promises settle (same limitation as ADR-002, not a new one).

Accepted

ADR-005: Bounded, Dependency-Aware Parallelization of Reads and Template Creates

Context

getTeamSettings/getWorkItem are independent but nested (Finding 2). The per-template create loop is serialized unconditionally (:61-64) though only justCreatedTasks-dependent templates genuinely need ordering (Finding 3, Insight 3). Interacts with ADR-002: more parallel templates means more of the batch is keepalive-protected.

Decision Drivers

  • Blanket parallelization would silently change existing templates' linking behavior — unacceptable for a stable, in-production extension.
  • Classification must reuse the existing linkTo-rule parsing in createWorkItem (:122-188) — no template schema change.
  • Classification also determines which templates get ADR-002's popup-close protection.

Considered Options

  1. Status quo, fully serialized
  2. Blanket-parallelize all creates — rejected, breaks justCreatedTasks-dependent templates
  3. Classify by linkTo-rule reference to justCreatedTasks helpers; parallelize the non-referencing group, keep the referencing group ordered; also parallelize getTeamSettings/getWorkItem — SELECTED

Decision Outcome

Option 3: real concurrency gains with no observed behavior change, and produces exactly the split ADR-002 depends on.

Consequences

Good: overlapping read latency; independent templates maximally keepalive-protected; ordered templates retain identical semantics.

Bad: classifier must stay in sync with any new linkTo rule types; requires careful implementation-time verification against existing template behavior before shipping.

TL;DR

A template field value whose trimmed form starts with = is evaluated by a new pure module src/scripts/expressionEvaluator.ts (tokenizer + recursive-descent parser, allowlisted grammar: numbers, + - * / %, unary minus, parentheses, {Field.Ref.Name} placeholders resolved from the parent, Math.ceil|floor|round|abs|min|max|pow); the finite numeric result is pushed into the child's JSON-Patch document. templateBuilder.ts gains the = branch (evaluated instead of replaceReferenceToParentField) and returns { patchDocument, skippedFields }; failures logError and skip the field, the child is still created, and TemplateOutcome.skippedFields drives a Warnings: <template> (N field(s) skipped) suffix in the existing completion dialog. Jest + ts-jest (CommonJS test tsconfig, tests in src/tests/) become the project's first test runner; README/overview/roadmap are updated and both manifests are set to 1.3.0 as the final step.

Key Decisions

  • createWorkItemFromTemplate returns { patchDocument, skippedFields } instead of an out-parameter — single caller, explicit and unit-testable, no mutable argument threading.
  • skippedFields attached only to created outcomes — a failed template is already flagged by name; the warning means "created but incomplete".
  • Placeholders resolved inside the evaluator; replaceReferenceToParentField is not called for = values — avoids undefined/null/2--3/string-injection failure modes; helper output stays byte-identical for non-= values.
  • One private typed error caught at the evaluateExpression boundary; the module never throws to callers — matches error-handling.md and the catch/log/degrade philosophy.
  • Evaluation during parsing (no AST) — tiny grammar, no second consumer; an AST would be a speculative abstraction.
  • formatCompletionMessage extracted from showCompletionDialog — the only way to unit-test the exact dialog wording without stubbing the VSS global.
  • Jest 29 / ts-jest 29; tsconfig.test.json extends tsconfig.json with module: commonjs, noEmit: true and a files entry for tfs.d.ts; no esModuleInterop — it would make the import * as Q from "q"; Q(...) pattern in childTypes.ts/templates.ts fail with TS2349. Type-only TFS/* imports are elided, no moduleNameMapper stub needed; gate: npx tsc --noEmit -p tsconfig.test.json (from src/) exits 0.
  • Version 1.3.0 for both manifests — new feature on top of the 1.2.8 already committed at HEAD 551aa91; new minor per the version-bump decision; package-lock.json realigned with npm install --package-lock-only.

Goal

Let template authors compute numeric child-field values from parent-field values with a safe, allowlisted arithmetic expression (=Math.ceil({Microsoft.VSTS.Scheduling.StoryPoints}*2)), while making every evaluation failure visible (console detail + dialog warning) without ever blocking child creation.

User Stories

Template authorWrite =Math.ceil({Microsoft.VSTS.Scheduling.StoryPoints}*2) in a task template's Story Points field so each generated task gets Story Points derived from its parent without manual editing.
Template authorA mistyped or unresolvable expression skips only that field, not the whole task, so a typo never stops the breakdown from being created.
User clicking "Create linked tasks"The completion dialog tells me which templates had fields skipped so I do not silently end up with tasks missing values.
Developernpm test runs unit tests for the evaluator, placeholder substitution, builder and dialog wording so parser changes are safe to make.
Marketplace userThe placeholder and expression syntax (including the integer-field rounding rule) is documented on the overview page so I can adopt the feature without reading source.

Grammar, API and Error Taxonomy

Public API (R2) 
isExpression(fieldValue: string): boolean
evaluateExpression(fieldValue: string, currentWorkItem: WorkItemFields): EvaluationResult
type EvaluationResult = { ok: true; value: number } | { ok: false; reason: string }
Grammar (R4) 
expression      = additive END ;
additive        = multiplicative { ( "+" | "-" ) multiplicative } ;
multiplicative  = unary { ( "*" | "/" | "%" ) unary } ;
unary           = "-" unary | primary ;
primary         = NUMBER | FIELD | call | "(" additive ")" ;
call            = IDENT "(" [ additive { "," additive } ] ")" ;
                  (* IDENT must be Math.<fn> *)

Precedence, highest first: parens/calls · unary minus · * / % (left) · + - (left). Examples: 1+2*3=7, (1+2)*3=9, 2*-3=-6, 10-4-3=3, --3=3.

primary on IDENT: next token ( → call; call not in the R5 table → unsupported function '<ident>'; IDENT without ( → unknown identifier '<ident>'. =abc(1) → unsupported function 'abc'; =Math.ceil → unknown identifier 'Math.ceil'.

Technical Approach

template.fields[key] (string, from ADO template API)
  -> IsPropertyValid(key)                       templateFilters.ts:177   (unchanged)
  -> '' ? inherit parent value                  templateBuilder.ts:14-18 (unchanged)
  -> isExpression(value) ?                      expressionEvaluator.ts   (new)
       yes -> evaluateExpression(value, currentWorkItem)
                ok    -> push { op:"add", path:"/fields/"+key, value:<number> }
                error -> logError(R10); skippedFields.push(key)
       no  -> replaceReferenceToParentField -> push string  (unchanged)
  -> { patchDocument, skippedFields }           templateBuilder.ts (R8)
  -> keepaliveFetch.createWorkItem(patchDocument)             (unchanged)
  -> outcome { templateName, status:"created", skippedFields? } workItemCreation.ts (R11)
  -> formatCompletionMessage -> showCompletionDialog          progressDialogController.ts (R13)
Evaluator internals, typing and transport notes
  • Hand-rolled tokenizer producing R3 tokens with their index; recursive-descent parser with one function per grammar rule returning numbers directly (evaluation during parsing, no AST). Placeholder lookup in primary when a FIELD token is consumed.
  • One module-private typed error carrying the reason; evaluateExpression wraps parsing in a single try/catch, maps it to { ok:false, reason }, maps anything else to unexpected error: …, then applies Number.isFinite. No shared state between calls.
  • ES2015, strict: true, camelCase, named exports, const/let, explicit return types on exports, JSDoc on exports only.
  • No type change in types.ts: the loop pushes string | number into WorkItemFields (value: any).
  • Transport unchanged: a JS number serialises as a JSON number; ADO validates Integer fields itself (400 → existing failed path).
  • Consistent with gap-analysis integration points 1-9; additions (BuiltWorkItem, formatCompletionMessage) stem from the Phase 2 failure-visibility scope expansion.

Known limitations
  • Only the final result is checked for finiteness; absorbed intermediate non-finite values (e.g. Math.min(1/0, 1)) succeed — consistent with JavaScript.
  • Numeric-string acceptance uses Number(): "0x10"/"1e3" convert; "Infinity" is rejected by the finite check.
  • "Child is still created" holds only for optional fields: a failing =expr on a required field (e.g. System.Title) is neither pushed nor backfilled, so ADO rejects the child (400) and the template is reported as Failed, not Warnings; the console still shows the R10 error. Documented in R19; no field-type lookup added.
  • replaceReferenceToParentField cannot log the template name (no template in its signature); its message identifies the template value instead.

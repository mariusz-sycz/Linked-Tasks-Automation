TL;DR

Compile with tsc invoked via the already-installed grunt-exec plugin (not grunt-ts, which is unmaintained), emitting AMD output to the unchanged scripts/app.js path. For the single 617-line app.js, bootstrap with JSDoc + allowJs/checkJs first to get compiler feedback while still in .js, then do a single-shot rename to .ts — classic multi-file "incremental leaf-first" migration doesn't apply to a one-file codebase. Type the VSS SDK via its own bundled typings/vss.d.ts/tfs.d.ts (no DefinitelyTyped needed) plus one hand-written declare const VSS for the non-AMD global; type Q via the current @types/q (v1.5.8, TS 4.5+). The no-test-suite risk has no tooling substitute — mitigate with small reversible commits and manual side-by-side .vsix comparison against a checklist.

Key Decisions

  • Use grunt-exec + direct tsc invocation, not grunt-ts — grunt-ts is confirmed unmaintained; grunt-exec is already a dependency and needs no new plugin.
  • JSDoc/checkJs bootstrap, then single-shot .ts rename — not a multi-file incremental rollout and not an unguarded big-bang rename either.
  • Type the VSS SDK from its own bundled typings/ folder, not DefinitelyTyped — vss-web-extension-sdk ships vss.d.ts, tfs.d.ts, rmo.d.ts covering the exact modules this project uses.
  • Keep @types/q; treat Q→native-Promise conversion as an optional, separately-scoped follow-up.
  • Do not adopt azure-devops-extension-sdk as part of this migration — it is a distinct, larger, non-drop-in migration.

Open Questions / Risks

  • No-test-suite mitigation pattern and the Q-to-native-Promise recommendation rest on WebSearch summaries only, never independently fetched.
  • azure-devops-extension-sdk v5.0.0's exact npm publish date could not be cross-verified; the "actively maintained" signal itself is solid.
  • Installed SDK version is 1.110.0 per lockfile, not ^1.104.0 as referenced in project docs — doesn't change the typing recommendation.

Full evidence and citations per finding

1. VSS SDK bundled types — vss-web-extension-sdk ships typings/vss.d.ts (core, controls, client services), tfs.d.ts (REST clients for Build/Work/Code — covers the exact modules this project uses), rmo.d.ts (unused). Two consumption patterns documented: "types": ["vss-web-extension-sdk"] in tsconfig.json, or /// <reference types="vss-web-extension-sdk" />. Requires only TS 2.5+. Source repo archived Jan 27, 2023 (maintenance-status flag, not a typings problem — types ship in every published version).

2. Ambient VSS global — used 12× in app.js (lines 89,512,529,536,538,541,542,544,547,549,551,601) but absent from the define([...]) array at app.js:1; injected via <script src="lib/VSS.SDK.min.js"> in toolbar.html:8 before module resolution. Needs a small declare const VSS: {...} covering getWebContext(), init(), require(), register().

3. Grunt integration — grunt-ts README: "This project... is now in a mature maintenance phase" / "Looking for Maintainers... I am no longer maintaining this plugin." Latest release 6.0.0-beta.22, ~6 years old, 72 open issues. grunt-exec (~0.4.7) is already installed and used for tfx-cli invocation (gruntfile.js:4-23) — reached independently by both the config gatherer (task-graph shape) and external gatherer (grunt-ts status).

4. @types/q freshness — latest v1.5.8, published Nov 7, 2023, targets TS 4.5+. Directly contradicts the research plan's prior staleness assumption.

5. Q not an npm dependency — exhaustive search of package-lock.json (6,700+ lines) found zero q package entries. vss-web-extension-sdk's lockfile node declares no dependencies. Runtime resolution happens via a Q-compatible implementation bundled inside VSS.SDK.min.js, registered under the "q" AMD module id by the SDK's own internal loader.

6. Codebase structure — app.js: 1 AMD module, 24 internal functions + 1 public method (create, app.js:597-614), 1 module-level mutable var (ctx, app.js:4). 3 of 7 AMD deps (Controls, StatusIndicator, Dialogs) unused (zero grep matches). Pre-existing bugs: implicit global at app.js:459 (for (category of categories), missing let/const); implicit global + property-read-off-pending-promise at app.js:526; dead function getWorkItemFormService (app.js:572-576) that synchronously returns before its promise resolves.

7. Clean tooling slate — Glob for **/tsconfig*.json and **/.eslintrc*: zero matches repo-wide. package.json devDependencies has no typescript, @types/*, or q; scripts: {} is empty.

8. Newer SDK scoping — azure-devops-extension-sdk latest 5.0.0, ships own SDK.d.ts, actively versioned, not archived. Porting article (Phong Cao) describes real changes required: remove libraryTarget: "amd", replace VSS.init()/VSS.require() with ES imports + sdkInit(), update REST client naming, handle field-shape changes (e.g. System.AssignedTo). New SDK's own README claims AMD compatibility retained — an unresolved but non-blocking ambiguity between sources.

9. Strategy adaptation — TS handbook recommends allowJs bootstrap + incremental per-file rename + progressive strictness. 2024-2026 industry sources (Patreon, Mixmax, Dylan Vann case studies, decision-matrix pieces) confirm incremental-by-default, "leaves first." app.js has no internal module boundaries — one file, flat function scope — so the leaf-first framing doesn't transplant. Adapted approach: JSDoc/checkJs bootstrap in .js, then single-shot rename.

10. No-test-suite mitigation — search-aggregated understandlegacycode.com content (not independently fetched this session): characterization/golden-master tests, small reversible commits, deriving correctness from multiple independent sources (compiler, IDE, linter, diff review). Adapted for this project: manual checklist per cataloged function, exercised side-by-side against pre/post-migration .vsix builds.

Analysis and Insights

Key Insights

1. The migration will fix bugs it wasn't asked to fix

Two implicit-global bugs and one sync-return-of-async-value bug are pre-existing defects a strict TS pass will force decisions on — not migration regressions. High

2. Incremental vs. big-bang is a false binary here

With one file, the file-count axis literature assumes doesn't exist. The real axis: does type-checking happen before or after the syntactic rename. Medium-High

3. Build tooling answer needed no new information

Two gatherers reached grunt-exec+tsc independently — from the task graph alone, and from grunt-ts's status. Convergence from unrelated angles. High

4. No-test-suite risk is process, not tooling

Unlike the other 3 success criteria (each resolved to a specific artifact), this resolves to ongoing behavior — structurally different and harder to verify as "done." Medium

Quality Assessment (SWOT)

Strengths

Zero new Grunt plugins; no DefinitelyTyped hunting; narrow, enumerable typing surface; clean tooling slate; compiler will surface real pre-existing bugs.

Weaknesses

No-test-suite risk has no tooling fix, only process discipline; single-shot rename still carries genuine risk even with JSDoc bootstrap.

Opportunities

Natural point to consolidate 3 duplicate logging functions and delete 3 dead AMD imports + 1 dead function; fold in version-mismatch cleanup.

Threats

vss-web-extension-sdk is archived — no vendor fixes for future SDK-level issues; the eventual newer-SDK migration is a second, larger, separately-risked project.

Conclusions

Direct answer: Compile with tsc via grunt-exec (not grunt-ts) to unchanged AMD output at scripts/app.js; type the VSS SDK from its own bundled declarations plus one small ambient VSS global, and type Q via the current @types/q; migrate the single app.js module via a JSDoc/checkJs bootstrap phase followed by a single-shot rename rather than either a classic multi-file incremental rollout or an unguarded big-bang rewrite; and treat the no-test-suite risk as a process problem solved by small commits and manual side-by-side .vsix verification, not a tooling gap.

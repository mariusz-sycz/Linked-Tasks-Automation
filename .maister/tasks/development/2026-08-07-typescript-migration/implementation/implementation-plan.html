TL;DR

Six strictly sequential task groups (1→2→3→4→5→6), mirroring the spec's own Technical Approach — this is a single-file port, not a parallelizable multi-module task. Groups 1-3 bootstrap tooling then fix/clean/rename app.js→app.ts while still reversible; Groups 4-5 wire and then actually verify the dual-packaging tsc build step (split because node_modules doesn't exist until Group 5's npm install); Group 6 is the manual .vsix side-by-side behavioral acceptance pass. No test framework is introduced — every group's “tests” are 2-8 manual verification checklist items (compiler output + code review + build-log inspection), per the task's explicit TDD-gate adaptation.

Key Decisions

  • Verification-checklist pattern replaces test-driven steps — no test framework exists or is introduced; each group substitutes 2-8 manual checklist items for the usual 2-8 automated tests.
  • All bug fixes (Core Req 8, 9, 10, 10a) and cleanup (Core Req 11-14) land in one group (Group 2), still as .js — matches the spec's bootstrap-before-rename sequencing; splitting would fragment one atomic reversible phase.
  • Grunt build-wiring split across two groups — Group 4 wires statically (code review only, no node_modules yet); Group 5 runs npm install then actually executes both packaging tasks to close the build-wiring orphan-risk finding for real.
  • Group 6 replaces the standard “Test Review & Gap Analysis” closing group — executes the spec's manual .vsix Implementation Guidance checklist end-to-end instead.
  • No Visual References / no visual-coverage.md — headless, non-UI migration; no design-context exists for this task.

Open Questions / Risks

Group 4's wiring verification is necessarily partial. Code review confirms the exec.tsc target and both registerTask array edits are textually correct, but only Group 5's actual grunt package-dev/grunt package-release runs (post npm install) truly close gap-analysis's build-wiring orphan-risk finding.
any/type-assertion fallback for loosely-typed .fields/JSON-Patch surfaces is undiscoverable until Group 5. The real shape of WorkItemTemplateReference/WorkItemTemplate typings is unverified until node_modules exists; expect small, scoped touch-ups to app.ts, not a rewrite.
Group 6 requires a real or sandbox Azure DevOps org. If unavailable, the spec's behavioral-parity Success Criteria (promise-chain ordering, seven linkTo branches) cannot be fully closed by this plan — flag back to the operator rather than marking Group 6 complete on compiler success alone.

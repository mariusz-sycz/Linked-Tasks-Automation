TL;DR

Port the single 617-line AMD module src/scripts/app.js to app.ts with strict: true, compiled via a new grunt-exec tsc target wired into both packaging paths, output landing unchanged at src/scripts/app.js. Bundled in the same pass (all pre-decided, zero new judgment calls): fix the broken promise chain, fix two implicit-global bugs, delete dead code (including one import this spec newly identifies as orphaned), consolidate logging, rename linkImtes→linkItems, and align package.json's version to the Marketplace-published 1.1.17. No UI change, no test framework, no new SDK.

Key Decisions

declare const VSS covers only the 4 methods actually called — getWebContext, init, require, register. No speculative surface for unused VSS APIs.
Compiled output emits in place, no outDir/rootDir remap — app.ts compiles directly back to src/scripts/app.js, the exact path both vss-extension.json and toolbar.html hardcode. Zero manifest/HTML changes.
TFS/WorkItemTracking/Services import added to the delete list — extends clarifications.md Q2. It's used only inside the dead getWorkItemFormService function; deleting that function makes this import dead by Q2's own "zero references" rationale. Not explicitly enumerated upstream — flagged here.
package.json's version becomes 1.1.17, adopting the already-published Marketplace value rather than rolling it back. Resolves a gap scope-clarifications.md left open ("include if trivial," no direction chosen).
AMD module contract preserved behaviorally, not byte-for-byte — tsc's AMD emit for export function create(...) populates a generated exports object instead of literally return { create }. The module value still exposes a callable .create(context), which is the actual contract toolbar.html depends on.
strict: true from the start, JSDoc/checkJs bootstrap → single-shot .ts rename — restates the binding tsconfig/sequencing target already decided upstream.

Open Questions / Risks

AMD-emit shape change (see Key Decisions) — low risk, but the manual checklist must exercise VSS.require(["scripts/app"], ...) end to end, not just individual functions.
Build-wiring dual-verification is a hard acceptance gate — both grunt package-dev and grunt package-release must independently invoke tsc; partial wiring is a silent-failure mode with zero test coverage to catch it.
VSS SDK's bundled .d.ts shape is unverified — node_modules isn't installed yet. Expect any/assertion fallback on the loosely-typed template .fields dictionary and JSON-Patch construction.
The promise-chain fix is a genuine behavior change, not risk-free — teams relying on (or coincidentally unaffected by) the current racy ordering could see different link graphs afterward. Checklist must specifically compare before/after link graphs for a 3+-template work item.

Goal

Migrate src/scripts/app.js to statically-typed TypeScript (strict: true) with zero required changes to toolbar.html or vss-extension.json, while fixing the promise-chain and implicit-global bugs the type system forces into the open, and folding in the roadmap's already-scoped Phase 1 cleanup items — all verified through a manual side-by-side .vsix checklist in place of automated tests.

User Stories

As an Azure DevOps user clicking "Create linked tasks," I want the exact same template-driven child-work-item creation behavior I have today, so that the migration is invisible to me except one correction: templates now create and link in the correct sequential order (previously racy).
As the maintainer, I want compile-time type checking across the REST client / template / work-item surface, so that future template-filtering changes fail fast in the editor instead of silently at runtime with no test suite to catch them.

Reusable Components

  • packaging.md — authoritative naming/wiring reference

New Components (justified)

  • Ambient declare const VSS — no AMD-typed analog for the script-tag global
  • Consolidated logger — collapses 4 near-duplicates, not new capability
  • 2 missing return statements — additive fix, not a component

Technical Approach

Sequencing: (1) tsconfig/devDependencies/ambient decl first, without touching app.js. (2) JSDoc/checkJs bootstrap — bug fixes and cleanup happen here, reversible as .js. (3) Single-shot rename to app.ts. (4) Wire + verify tsc in both packaging paths. (5) npm install to materialize node_modules and confirm SDK typings cover the actual response shapes read.

Module contract: each AMD dependency becomes a TS import whose specifier string matches today's define([...]) entry exactly, preserving runtime module-id resolution. VSS stays outside the import list (global, per ambient declaration).

Data flow: unchanged shape — create(context) → AddTasks → typed REST calls → template fetch/validate/filter → JSON-Patch construction → createWorkItem → linkItems. The promise-chain fix changes timing only.

Implementation Guidance

Verification Approach (no automated tests — TDD gate adapted)

Each implementation step group gets a manual verification checklist of 2-8 items, exercised side-by-side against a real/sandbox Azure DevOps org's pre- vs. post-migration .vsix, mirroring the standard per-group test-count guidance without writing test code.

Must cover at minimum: IsValidTemplateWIT/IsValidTemplateTitle (JSON + legacy filter syntax), SortTemplates ordering, the promise-chain fix (3+ templates, sequential creation + justCreatedTasks ordering), all six linkTo directive branches, the AsTasks/AsRequirements bugsBehavior branches, and the VSS.require module-resolution path end to end. Build-pipeline dual-invocation is a separate, explicit checklist item.
